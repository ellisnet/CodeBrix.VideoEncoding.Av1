WHY THIS FILE EXISTS
--------------------------------------------------------------------------------
A binary in a package is anonymous. This file is how anyone later can tell which
native library came from which source, which toolchain and which build machine.
Every time a binary is adopted into ../src/CodeBrix.VideoEncoding.Av1/runtimes/
<rid>/native/, its section here is updated from that build's
output/<rid>/BUILD-INFO.txt.

Known libaom behaviours (libaom 3.15.2, measured 2026-10-10)
--------------------------------------------------------------------------------
  1. SEQUENCE HEADER. aom_codec_get_global_headers() right after init returns a
     sequence header whose coding-tool flags (use_128x128_superblock,
     enable_interintra_compound, enable_dual_filter, enable_jnt_comp,
     enable_restoration) and, at 12 bits, subsampling + chroma sample position
     differ from the one libaom writes into the key frames (it finalises them
     at the first frame). The shim therefore reports the OBU_SEQUENCE_HEADER of
     the first key-frame packet (contract amended accordingly); the smoke test
     checks it equals the one inside every key frame.
  2. FORCED KEY FRAMES. In GOOD_QUALITY usage a frame encoded with
     AOM_EFLAG_FORCE_KF at N is followed by a SECOND real key frame at N+1 -
     with automatic key frames on or off (CBA_OPT_AUTOMATIC_KEY_FRAMES), with
     the default look-ahead and with lag 0, at every cpu-used; forcing frame 0
     gives 0 and 1. REALTIME gives exactly N; ALL_INTRA keys every frame. Cause
     (lag > 0): av1/encoder/pass2_strategy.c, find_next_key_frame() ->
     define_kf_interval(search_start_idx = 1) -> detect_app_forced_key() scans
     the look-ahead from index 0, i.e. the forced frame itself, so the new
     key-frame group gets length 0. Unchanged on libaom main (2026-10-10). A
     15-line candidate fix (scan from search_start_idx) removed the N+1 key
     frame for lag > 0 in a scratch build (smoke test still green) but not for
     lag 0; it is NOT APPLIED (aom/ stays unmodified; patches/ is empty). Kept
     here as the basis of a possible upstream report:
       file     aom/av1/encoder/pass2_strategy.c
       function define_kf_interval()
       change   replace
                    int num_frames_to_next_key = detect_app_forced_key(cpi);
                with a scan of the look-ahead that starts at search_start_idx
                instead of 0:
                    int num_frames_to_next_key = -1;
                    for (int k = search_start_idx; k <= cpi->ppi->lookahead->max_sz; k++) {
                      const struct lookahead_entry *e =
                          av1_lookahead_peek(cpi->ppi->lookahead, k, cpi->compressor_stage);
                      if (e == NULL) break;
                      if (e->flags == AOM_EFLAG_FORCE_KF) { num_frames_to_next_key = k; break; }
                    }
       effect   (lag > 0) forced key frame at N -> key frames 0, N only (was
                0, N, N+1); the lag-0 path is a different one and still keys N+1.
     (The same diff as a patch file: ClaudeHome/CANDIDATE_libaom-3.15.2_forced-
     kf-double-keyframe_2026-10-10.patch.) Consequence for lock-step pairs: two
     encoders given the same forced frames still produce IDENTICAL key-frame
     positions (N and N+1 in both) - proven by the smoke test with automatic
     key frames off and a scene cut in one stream only.
  3. LOSSLESS AT 10 BITS WITH LOOK-AHEAD IS NOT BIT-EXACT. Reproduced with
     libaom's own aomenc (built host-only from aom/, never shipped) on the
     managed tests' fixtures, decoded identically by aomdec and dav1d: a few
     wrong samples on some inter frames, content- and size-dependent (10-bit
     I420 crops of one source at widths 136/162/164/166/168/200 x 92 bad,
     others exact; 10-bit MONOCHROME 320x180 bad on two frames through the
     shim). Independent of cpu-used, threads, arnr-*, overlay, keyframe
     filtering, tpl (partial). Exact in every case tried with lag-in-frames 0
     or with enable-order-hint 0; 8-bit was exact. => The shim encodes LOSSLESS
     with lag 0, always.
  4. ODD-SIZED 4:2:0. libaom does not code the last chroma column (odd width)
     or row (odd height) of an I420 picture faithfully - every frame, key
     frames included, lossless, lag 0 or not, through aom_img_wrap AND through
     aom_img_alloc + copy, aomenc too; I444 and MONOCHROME odd sizes are exact.
     => create() refuses odd width/height for CBA_LAYOUT_I420.
  5. Matrix coefficients 0 (identity) with subsampled input: libaom refuses it
     at the first encode; the shim refuses it at start (CBA_E_UNSUPPORTED)
     unless the layout is I444.
